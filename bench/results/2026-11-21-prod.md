# ircd bench

Measured 2026-11-21 10:55:55 UTC against `127.0.0.1:16667`.
Welcome numeric: `:irc.example.org 001 b25278296 :Welcome to IRC b25278296!b25278296@172.17.0.1`.
Load generator event loop: `rsloop`.

This is the production image (`Dockerfile.prod`: the release with
ERTS included, on Debian slim) run as `docker-compose.prod.yml` runs it:
`config/ircd.prod.json` (flood limits, DroneBL, `channels` retention,
JSON info logging) with only `max_clients` raised so the high-load
clients fit, `ulimit -n` 65536, `init`, and a fresh data volume, on
another host port (`bench/prod`).
Load generator: host CPython asyncio through the published port.
One container sample taken during registration: `ircd-prod-bench cpu=3.83% mem=133.3MiB / 31.26GiB`.
OTP/ERTS: `ERTS 17.1.1, release 0.1.0`.
Warmed up with 50 registrations before the measured phases.

## Traffic

- Sequential `PING`/`PONG`, 100 samples, 0 errors.
  p50 0.42 ms, p95 0.52 ms, p99 0.61 ms.
- Pipelined `PING`, 400 of 400 `PONG` replies in 0.066s (6031.4/s).
- Registration, 200 welcomes of 200 attempts, concurrency 32, 1.022s (195.6/s). Welcome p50 16.27 ms, p95 22.15 ms. Errors: 0.
- Channel `PRIVMSG`: 8 members, 800 messages sent, 5600 of 5600 deliveries in 0.652s (8594.6/s deliveries).

A sender does not receive its own channel message, so the expected
delivery count is `members * messages_each * (members - 1)`.
Clients quit at the end of each phase. Nicks stay reserved for 60 seconds.

`PING <marker>`; latency is the time until that PONG, so it covers the whole
reply. Errors count 4xx/5xx numerics, `FAIL` replies, and timeouts.
The client is paced to at most 40 lines per second (below
the server's flood limit); the pause is outside the measured latency, so
ops/s reflects the pacing, not the server's capacity.
